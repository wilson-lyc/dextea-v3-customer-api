# 代码目录结构重构方案

> 适用项目：`github.com/dextea-v3/dextea-customer/api`（基于 Gin 的顾客端 HTTP API）
> 调研时间：2026-08-20

本文在梳理当前目录结构的基础上，指出痛点，并给出两套可选的重构方案（轻量版 / 标准分层版），最后给出迁移建议与落地步骤。

---

## 1. 当前结构现状

```
.
├── cmd/
│   └── server/
│       └── main.go              # 程序入口：加载配置、调用 biz.New 装配、启动 HTTP Server
├── docs/
│   └── 支付宝登录实现.md
├── internal/
│   ├── alipay/                  # 支付宝 OAuth 客户端（独立 sdk 式封装，~8KB 单文件）
│   ├── biz/                     # ★ 业务层（核心，36 个文件）
│   │   ├── app.go               # 组合根：连接 DB/Redis、装配所有模块、构建 gin.Engine
│   │   ├── area/                # handler/dto/errorcode/service/repository/module
│   │   ├── customer/            # handler/dto/errorcode/model/service/repository/module
│   │   ├── menu/                # handler/dto/model/service/repository/module
│   │   ├── order/               # handler/errorcode/service/module（转发到 Java 订单服务）
│   │   ├── product/             # handler/dto/model/service/repository/module
│   │   └── store/               # handler/dto/model/service/repository/module
│   ├── common/                  # 跨层公共组件
│   │   ├── bizerror/            # 业务错误定义与包装
│   │   └── response/            # 统一 HTTP 响应
│   ├── config/                  # config.go 单文件：配置加载、校验、DSN 拼接
│   ├── jwt/                     # jwt.go 单文件：token 签发与解析
│   ├── middleware/              # auth.go / cors.go / exception.go
│   ├── mysql/                   # mysql.go 单文件：sqlx 连接
│   ├── redis/                   # redis.go 单文件：redis 连接
│   ├── router/                  # router.go 单文件：gin 引擎构建 + 全局中间件
│   └── server/                  # registerable.go 单文件：Registerable 装配契约接口
├── go.mod
└── go.sum
```

### 已具备的良好实践

- **组合根（Composition Root）清晰**：`biz.New(cfg)` 是唯一装配点，依赖显式注入，没有包级全局单例满天飞。
- **模块装配契约统一**：`server.Registerable`（`Register(*gin.Engine)`）解耦了 router 与具体业务，新增模块无需改 router/main。
- **业务模块内部分层统一**：绝大多数模块遵循 `handler → service → repository` 的调用链，并辅以 `model / dto / errorcode / module`。
- **统一响应与错误模型**：`common/response`、`common/bizerror` 已被各模块复用。

---

## 2. 当前痛点分析

### 2.1 `biz` 包承担了“业务层”和“应用装配层”两重职责
`internal/biz/app.go` 里既做基础设施连接（`mysql.New`、`redis.New`、`alipay.New`），又做全部模块的装配与 `gin.Engine` 构建。随着模块增多，`New` 函数会持续膨胀，且**应用装配逻辑**与**业务代码**混在同一包，职责边界模糊。

### 2.2 基础设施层散落在 `internal` 顶层，缺乏归类
`mysql`、`redis`、`config`、`jwt`、`alipay`、`middleware`、`router`、`server` 八类东西平铺在 `internal/` 下：
- `mysql`/`redis`/`config`/`jwt`/`alipay` 本质是**基础设施（infrastructure）**；
- `middleware`/`router`/`server` 是**传输/装配层（transport/assembly）**；
- 全部平级，无法一眼区分“框架粘合代码”与“第三方封装”。

### 2.3 模块内文件集合不统一，缺漏随意
以 `area` 为例有 `dto` 无 `model`；`order` 有 `errorcode` 但无 `dto/model/repository`（因为它是转发代理）；`menu` 有 `model` 但 `repository.go` 里其实混了业务逻辑。这种“按需缺省”导致新成员无法形成稳定预期，IDE 里一个目录里究竟是 6 个文件还是 3 个文件全凭记忆。

### 2.4 重复的常量与 header 定义
- `CustomerIDHeader = "X-Customer-Id"` 在 `middleware/auth.go` 与 `biz/order/handler.go` 中**各自定义了一份**（值相同，来源不同），一旦改名极易漏改。
- `order` 模块里 `40100` 等错误码硬编码在 handler，而 `area` 用的是 `errorcode.go` 里的 `BizError`，错误码管理体系不统一。

### 2.5 `common` 与 `bizerror` 的命名层级
`common/bizerror` 与 `common/response` 已经是很好的公共沉淀，但“业务错误码”放在 `common` 下，意味着它和传输层（`response`）同级；从语义上，错误码更贴近业务，可考虑上提到业务域或独立为 `errors` 包。

### 2.6 缺少 obvious的“不编译进 binary 的支撑目录”
没有 `scripts/`、`build/`、`deploy/`、`test/`、`api/`(openapi) 等目录，CI/CD 与接口契约目前无处安放（虽然当前可能不是强需求，但结构预留更利于长期演进）。

---

## 3. 重构目标

1. **按“层（layer）”而非“平铺”组织基础设施与传输代码**，让目录即文档。
2. **保持现有分层约定（handler/service/repository）不变**，仅在模块目录上做收敛或分组，降低业务代码改动风险。
3. **消除重复的跨层常量/错误码定义**，集中到单一来源。
4. **最小化 main 包与组合根的膨胀**，把“应用装配”从“业务”中剥离。
5. **重构不引入破坏性 API 变更**，可逐步灰度迁移。

---

## 4. 方案 A：轻量整理（推荐先做，低风险）

**核心思路**：只调整 `internal` 顶层的归类，业务模块 `biz/*` 内部几乎不动。改动小、编译安全、易 review。

### 4.1 目标结构

```
internal/
├── biz/                         # 仅保留业务模块（area/customer/menu/order/product/store）+ 各自的 handler/service/repository...
│   ├── app.go                   # 仍然作为组合根，但只“引用” infra，不再内联连接细节（见 4.3）
│   ├── area/
│   ├── customer/
│   ├── menu/
│   ├── order/
│   ├── product/
│   └── store/
├── infra/                       # 新增：所有第三方/存储基础设施封装
│   ├── mysql/
│   ├── redis/
│   ├── config/
│   ├── jwt/
│   └── alipay/
├── transport/                   # 新增：HTTP 传输与装配相关
│   ├── middleware/
│   ├── router/
│   └── server/                  # Registerable 契约
├── common/                      # 跨域公共（保持）
│   ├── bizerror/
│   └── response/
└── pkg/                         # 可选：可被外部复用的纯工具（如错误码、常量）
    └── consts/                  # 集中 X-Customer-Id、API 前缀等共享常量
```

### 4.2 迁移动作

| 动作 | 旧路径 | 新路径 |
|------|--------|--------|
| 移动 | `internal/mysql` | `internal/infra/mysql` |
| 移动 | `internal/redis` | `internal/infra/redis` |
| 移动 | `internal/config` | `internal/infra/config` |
| 移动 | `internal/jwt` | `internal/infra/jwt` |
| 移动 | `internal/alipay` | `internal/infra/alipay` |
| 移动 | `internal/middleware` | `internal/transport/middleware` |
| 移动 | `internal/router` | `internal/transport/router` |
| 移动 | `internal/server` | `internal/transport/server` |
| 新增 | — | `internal/pkg/consts`（集中 `CustomerIDHeader`、API 前缀） |

> 由于 Go 的包路径即导入路径，移动后只需全局替换 import 前缀（`internal/mysql` → `internal/infra/mysql` 等），`gofmt`/`goimports` 可一键完成。

### 4.3 组合根瘦身（可选但建议）

将 DB/Redis/Alipay 的连接细节下沉到 `infra` 各自的 `New`，`biz/app.go` 只负责“调用 + 装配”：

```go
// internal/biz/app.go（重构后片段）
db, err := mysql.New(cfg.DatabaseDSN())          // 连接细节留在 infra/mysql
rdb, err := redis.New(cfg.RedisAddr, ...)        // 连接细节留在 infra/redis
// ... 装配 handlers（不变）
```

这一步不改变任何对外行为，仅把“连接字符串拼接/重试/超时”等细节留在 infra 包内。

### 4.4 消除重复常量

新增 `internal/pkg/consts/consts.go`：

```go
package consts

const (
    CustomerIDHeader = "X-Customer-Id"
    APIPrefixV1      = "/api/v1"
)
```

`middleware/auth.go` 与 `biz/order/*` 统一从 `consts` 引用，`order` 模块自身的 `CustomerIDHeader`/`goAPIPrefix` 定义删除。

## 5. 方案 B：标准 DDD 风格分层（中长期演进）

**核心思路**：在方案 A 基础上，把 `biz` 进一步显式拆为 `domain`（业务实体/错误码）与 `application`（用例编排），并对模块做“按域分组”。改动较大，适合团队规模扩大、模块继续增加时。

### 5.1 目标结构

```
internal/
├── domain/                      # 业务内核：实体、值对象、领域错误（不依赖 gin/sqlx）
│   ├── customer/
│   │   ├── model.go             # Customer 实体、Platform 值对象
│   │   └── errors.go            # 该域专属 BizError（原 errorcode.go 上提）
│   ├── store/
│   ├── product/
│   ├── menu/
│   ├── order/                   # 转发代理域，无实体
│   └── area/                    # 外部 API 适配域
├── application/                 # 用例层：service + handler（编排 domain 与 infra）
│   ├── customer/
│   │   ├── service.go
│   │   └── handler.go
│   └── ...（其他域同构）
├── infra/                       # 同方案 A
│   ├── mysql/
│   ├── redis/
│   ├── config/
│   ├── jwt/
│   └── alipay/
├── transport/                   # 同方案 A
│   ├── middleware/
│   ├── router/
│   └── server/
├── common/
│   ├── response/
│   └── errors/                  # 全局基础错误（ErrInternal 等），替代 common/bizerror 的“通用部分”
└── pkg/
    └── consts/
```

### 5.2 关键变化

- **`domain` 不依赖 `gin`/`sqlx`**：实体与领域错误成为纯 Go 类型，`repository` 改为接口定义在 `domain`，实现留在 `infra`。这能彻底解耦业务规则与存储细节，便于单测。
- **`errorcode.go` 上提为 `domain/<域>/errors.go`**：错误码与实体同属一个域，语义更内聚；全局通用错误（`ErrInternal`/`ErrOK`）下沉到 `common/errors`。
- **`model.go` 从各 `biz/<域>` 移动到 `domain/<域>`**：`json`/`db` tag 保留在实体上（务实做法），或拆为 `domain` 纯实体 + `infra` 持久化映射（更彻底但工作量更大）。

### 5.3 风险与成本

- 跨包引用关系大规模调整，需要重跑全部单测与编译。
- 若当前团队规模小、模块稳定，**方案 A 已足够**，方案 B 可标记为“未来方向”而非立即执行。

---

## 6. 两套方案对比

| 维度 | 方案 A（轻量整理） | 方案 B（DDD 分层） |
|------|-------------------|-------------------|
| 改动范围 | 仅移动 `internal` 顶层包 + 新增 consts | 重排全部业务包，引入 domain/application 分层 |
| 编译风险 | 极低（仅 import 路径变化） | 中（跨包依赖重排） |
| 业务代码改动 | 几乎无 | 中（model/errorcode 迁移） |
| 可测试性提升 | 无 | 显著（domain 可独立单测） |
| 适合阶段 | 当前即可执行 | 模块继续扩张、团队扩编后 |
| 推荐度 | ★★★★★（先落地） | ★★★（作为演进路线） |

---

## 7. 统一规范建议（无论选哪套都该做）

1. **模块文件清单标准化**：约定每个业务域至少包含
   `handler.go / service.go / repository.go / model.go / dto.go / errorcode.go / module.go`，
   没有的用“空实现或显式注释 `// 本域无持久化`”占位，避免“到底有没有这个文件”的认知负担。
2. **错误码集中管理**：全局通用错误放 `common/errors`，域专属错误放各域 `errors.go`，handler 中**禁止硬编码** `40100` 等业务码。
3. **共享常量单一来源**：`X-Customer-Id`、`/api/v1` 前缀等只允许在 `pkg/consts` 定义一次。
4. **`order` 模块治理**：它是转发代理，建议显式标记为 `pkg/orderproxy` 或在目录加 `README` 说明“本模块不持有实体，仅透传”，避免后续维护者误以为它缺文件是 bug。
5. **补充支撑目录**（按需）：`scripts/`（本地脚本）、`deploy/`（部署清单）、`api/`（OpenAPI 契约），让非源码资产有归属。

---

## 8. 落地步骤（建议顺序）

1. **第 1 步**：新建 `internal/pkg/consts`，收敛 `CustomerIDHeader`、API 前缀，替换 `middleware` 与 `order` 中的重复定义。编译验证。
2. **第 2 步**：执行方案 A 的目录移动（`infra/`、`transport/`），用 `goimports -w` 重写 import。编译 + 跑现有测试。
3. **第 3 步**：把 `biz/app.go` 中的连接细节下沉到 `infra` 各包（仅重构，不改变行为）。
4. **第 4 步**：补齐各业务域缺失文件（占位或注释），统一错误码不硬编码。
5. **第 5 步（可选，远期）**：评估是否启动方案 B，将 `domain` 与 `application` 分离。

---

## 9. 小结

当前项目分层思想已经比较健康（组合根清晰、Registerable 解耦、统一响应/错误），主要问题是**顶层包平铺、缺乏层级归类、少量重复定义**。

优先执行低风险的**方案 A**：把基础设施收进 `infra/`、传输与装配收进 `transport/`、共享常量收进 `pkg/consts`，即可显著提升目录可读性，且几乎零业务改动。方案 B 作为模块进一步膨胀时的演进路线保留。
