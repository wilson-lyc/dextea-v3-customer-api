# 异常处理机制重构方案

> 本文档在对标阿里《Java 开发手册》、Uber Go Style Guide、Google SRE 等业界实践的基础上，
> 结合本项目（Go + Gin + 微服务网关）的现状，给出一套可落地的异常处理重构方案。
>
> 适用范围：本仓库所有 HTTP 接口、业务 Service、下游（Java 订单中台）透传转发层。

---

## 1. 现状梳理

当前系统已经具备的基础能力：

| 能力 | 现有实现 | 位置 |
| --- | --- | --- |
| 全局异常拦截 | `ExceptionInterceptor` 通过 `recover` 兜底，区分业务异常 / 系统异常 | `internal/transport/middleware/exception.go` |
| 统一响应结构 | `APIResponse{Code, Message, Data}` | `internal/common/response/response.go` |
| 业务错误码 | `BizError{Code, Message}` + `As/New` | `internal/common/bizerror/bizerror.go` |
| 系统错误收敛 | 未知错误统一透出 "服务异常，请稍后重试"，底层细节仅落日志 | `response.ErrorOf` |
| 下游错误封装 | 订单转发层用 `bizerror.New` 包装网络 / 配置类错误 | `internal/biz/order/service.go` |

### 1.1 当前存在的问题（对照大厂实践）

1. **错误码缺乏统一分段规范**。现有码值随意（如 `50000`、`50300`、`42001`、`40100`、`40001`），未形成"系统码 / 业务码 / 模块码"的分层约定，跨模块易冲突、难排障。
2. **错误类型不够丰富**。目前只有"业务异常"与"兜底系统异常"两类，缺少：参数校验错误、下游依赖错误、超时 / 限流、幂等冲突等更细的分类。
3. **错误信息存在"双轨制"**。handler 中大量手写 `response.Error(c, ..., 40100, "未登录或登录已过期")`，
   同一文案与码值散落多份（见 `internal/biz/order/handler.go`），违反"错误码 / 文案由统一错误中心定义，业务代码只引用"的原则。
4. **缺少结构化错误上下文（cause / fields）**。`BizError` 没有携带根因（wrapped error）和上下文字段，
   排障时只能靠日志反查，无法在错误对象内携带 `orderId`、`customerId` 等定位信息。
5. **`As` 只支持 `*BizError` 直接断言**，无法识别被 `fmt.Errorf("%w")` 包裹后的业务错误，链路包装后类型信息丢失。
6. **HTTP 状态码与业务码语义割裂**。业务错误统一返回 `200 OK`，前端只能靠 `code` 判断；部分 handler 又混用 `401`/`400` 的 HTTP 状态，约定不统一。
7. **缺少重试 / 幂等 / 熔断等韧性（resilience）语义**。下游（订单中台）调用失败时直接报错，没有超时分级、重试、降级策略。
8. **缺乏对外的错误码文档 / 枚举暴露机制**，前端、测试无法获得权威码表。

## 2. 业界大厂实践要点（对标）

### 2.1 阿里巴巴《Java 开发手册》—— 异常与错误码规约
- **错误码分层分段**：建议错误码为纯数字、具备可读性分段，如 `[系统标识][模块][具体错误]`，同类型错误码可排重。
- **错误码不可使用纯数字 0 表示失败**，0 仅表示成功。
- **不要生吞异常 / 大段 try-catch**，应精准捕获；捕获后必须处理（记录日志或转换）。
- **禁止用异常做流程控制**，异常只用于异常场景。
- **错误提示信息要收敛、避免暴露敏感信息**（SQL、堆栈、内部路径）。
- **`@ControllerAdvice` + `@ExceptionHandler`** 做全局统一异常处理，本项目对应 `ExceptionInterceptor`。

### 2.2 Uber Go Style Guide —— 错误处理
- **优先返回 error 而不是 panic**；panic 仅用于真正不可恢复的程序错误。
- **错误要包装（wrap）并携带上下文**：`fmt.Errorf("xxx: %w", err)`，保留根因链。
- **使用 `errors.Is` / `errors.As` 做错误判定**，而不是字符串匹配或直接类型断言。
- **不要忽略错误**（不要 `_ = doSomething()`）。
- **不要在库代码中 log-and-return 同一个 error 两次**（避免重复日志）；决定权交给顶层。

### 2.3 Google SRE / 微服务韧性
- **错误预算（Error Budget）与 SLI/SLO**：把"错误率"作为核心稳定性指标，而非仅看是否 panic。
- **错误分类（error taxonomy）**：区分"用户错误（4xx）"与"服务端错误（5xx）"，二者计入 SLO 的口径不同。
- **超时、重试、退避、熔断（circuit breaker）、降级**是调用下游的标准韧性手段。
- **关联追踪（trace id）贯穿错误链路**，本项目已通过 OpenTelemetry 注入，应坚持下去。

### 2.4 错误码设计共识（微服务）
- 业务码应使用高位段（如 10000+）以区别于系统码（参考斗鱼 / 腾讯 Jupiter 框架 `pkg/ecode` 约定）。
- 跨服务调用（gRPC ↔ HTTP 网关）错误码应能互相映射，保证链路一致。
- 每一类可恢复错误都应能映射到"是否可重试（retryable）""是否需要告警（alertable）"等元数据。

## 3. 目标设计

### 3.1 错误分类与错误码分段规范

约定错误码为 **6 位纯数字**，分段如下：

```
A B C D E F
│ │ │ │ │ └─ 具体错误序号（00~99）
│ │ │ │ └─── 功能模块（00~99）
│ │ │ └───── 服务/系统标识（固定，避免与下游冲突）
│ │ └─────── 宏观错误类（1=系统, 2=业务, 3=下游依赖, 4=参数/校验, 5=限流/幂等）
│ └───────── 预留/保留位
```

| 段位 | 含义 | 示例 |
| --- | --- | --- |
| `1xxxxx` | 系统错误（基础设施、未知 panic） | `10000` 内部错误、`10300` 数据库未启用 |
| `2xxxxx` | 业务错误（领域规则不满足） | `20001` 订单已取消不可支付 |
| `3xxxxx` | 下游依赖错误（调用订单中台等失败） | `30001` 下游服务未配置、`30002` 下游不可用 |
| `4xxxxx` | 参数 / 校验错误 | `40001` 参数缺失、`40100` 未登录 |
| `5xxxxx` | 限流 / 幂等 / 熔断 | `50001` 请求过于频繁、`50002` 重复提交 |

> 说明：当前 `50000/50300` 等旧码在迁移期保留并逐步收敛到新分段，避免一次性破坏前端契约。

### 3.2 增强 `BizError` 结构

为支持分类判定、根因携带、上下文注入，扩展错误模型：

```go
package bizerror

import (
    "fmt"
    "errors"
)

// Kind 表示错误宏观类别，决定 HTTP 映射、是否可重试、是否告警。
type Kind int

const (
    KindSystem    Kind = 1 // 系统错误
    KindBusiness  Kind = 2 // 业务错误
    KindDownstream Kind = 3 // 下游依赖错误
    KindValidation Kind = 4 // 参数/校验错误
    KindFlowControl Kind = 5 // 限流/幂等/熔断
)

type BizError struct {
    Code    int
    Message string
    Kind    Kind
    Cause   error             // 根因（可空），用 %w 语义保留
    Fields  map[string]interface{} // 排障上下文，如 orderId/customerId
}

// New 基于已定义错误模板创建实例，可覆盖 message、附带 fields、绑定根因。
func New(tpl *BizError, opts ...Option) *BizError { ... }

// 实现标准 error 接口（Error/Unwrap），从而可被 errors.Is/As 识别。
func (e *BizError) Error() string { ... }
func (e *BizError) Unwrap() error { return e.Cause }

// 元信息方法：供中间件与 response 层决策。
func (e *BizError) Retryable() bool { return e.Kind == KindDownstream || e.Kind == KindFlowControl }
func (e *BizError) Alertable() bool { return e.Kind == KindSystem }
func (e *BizError) HTTPStatus() int { ... } // 由 Kind 推导默认 HTTP 状态码
```

### 3.3 统一错误中心（集中定义，业务只引用）

废除 handler 中手写文案的做法，所有错误在 `bizerror` 包内集中定义，并按模块分组：

```go
// internal/common/bizerror/common.go —— 通用错误
var (
    ErrOK          = &BizError{Code: 0,     Message: "ok", Kind: KindBusiness}
    ErrInternal    = &BizError{Code: 10000, Message: "内部错误", Kind: KindSystem}
    ErrUnauthorized= &BizError{Code: 40100, Message: "未登录或登录已过期", Kind: KindValidation}
    ErrBadRequest  = &BizError{Code: 40001, Message: "参数不合法", Kind: KindValidation}
)

// internal/common/bizerror/downstream.go —— 下游依赖错误
var (
    ErrOrderNotConfigured = &BizError{Code: 30001, Message: "订单服务未配置", Kind: KindDownstream}
    ErrOrderUnavailable   = &BizError{Code: 30002, Message: "订单服务暂不可用", Kind: KindDownstream}
    ErrOrderFailed        = &BizError{Code: 30003, Message: "订单服务处理失败", Kind: KindDownstream}
)
```

业务模块（如 `order`、`customer`）的专属错误放在各自 `errorcode.go` 中，引用通用模板风格统一定义，避免散落。

### 3.4 升级 `response` 与 `ErrorOf`

让响应层依据 `Kind` 决定 HTTP 状态码，并支持带 `fields` 的结构化输出（仅内部可见字段不回显）：

```go
func ErrorOf(c *gin.Context, err error) {
    if b, ok := As(err); ok {
        // 业务/下游/校验错误：用 Kind 推导 HTTP 状态（4xx 或 200+业务码）
        httpStatus := b.HTTPStatus()
        Error(c, httpStatus, b.Code, b.Message)
        // 严重错误（系统类）额外告警
        if b.Alertable() {
            applog.Error(c.Request.Context(), "alertable error", zap.Error(err))
        }
        return
    }
    // 未知错误：兜底 + 告警 + trace 记录
    applog.Error(c.Request.Context(), "unhandled error", zap.Error(err))
    Error(c, http.StatusInternalServerError, ErrInternal.Code, "服务异常，请稍后重试")
}
```

`As` 应基于 `errors.As(err, &target)` 实现，以兼容被 `fmt.Errorf("%w")` 包装后的业务错误：

```go
func As(err error) (*BizError, bool) {
    var b *BizError
    if errors.As(err, &b) {
        return b, true
    }
    return nil, false
}
```

### 3.5 增强全局异常拦截器

在现有 `ExceptionInterceptor` 基础上：

- **分类记录**：`Kind=System` 记录 error 级 + 堆栈并触发告警；其余记录 warn/info。
- **收敛对外信息**：无论何种异常，绝不回显 SQL、堆栈、内部路径；根因仅在日志出现。
- **保持 `c.Writer.Written()` 判断**，避免重复 `WriteHeader`。
- **panic 安全兜底**：仍捕获 `recover`，但把有意 `panic(*BizError)` 与无意 `panic(any)` 区分对待。

### 3.6 下游（订单中台）调用的韧性策略

针对 `internal/biz/order/service.go` 的 `Forward`：

- **超时分级**：单次请求 `10s` 超时（已有），并对"建单"等关键路径更短超时。
- **有限重试 + 指数退避**：仅对 `KindDownstream`（网络瞬时失败）重试 1~2 次，且下游需幂等。
- **熔断**：连续失败达到阈值时快速失败，返回 `50001 下游熔断`，保护本服务。
- **降级**：可降级接口（如"查询制作状态"）在下游不可用时返回缓存/默认值而非硬错。
- **错误携带上下文**：`bizerror.New(ErrOrderUnavailable, bizerror.WithCause(err), bizerror.WithField("target", target))`。

### 3.7 可观测性与错误码文档化

- 所有错误统一带 `trace_id`（已通过 OTel 实现），日志结构化输出 `code/kind/fields`。
- 提供脚本或代码生成，导出全部 `BizError` 码表为 `docs/error-codes.md`，供前端/测试/运维查阅。
- 对 `Kind=System` 与高频 `KindDownstream` 配置告警规则，纳入 SLO 错误率统计。

## 4. 落地步骤（建议顺序）

1. **定义错误分段规范与 `BizError` 增强模型**（§3.1、§3.2），保证向后兼容（保留旧码）。
2. **建设统一错误中心**：把 `response.Error(c, httpStatus, code, msg)` 的散落文案，迁移为引用 `bizerror` 模板（重点清理 `internal/biz/*/handler.go` 中的重复 40100/40001）。
3. **升级 `response.ErrorOf` 与 `As`**（§3.4），改用 `errors.As`。
4. **增强 `ExceptionInterceptor`**（§3.5）的分类日志与告警。
5. **为订单转发层补充重试 / 熔断 / 降级**（§3.6）。
6. **生成错误码文档与告警接入**（§3.7）。
7. **补充单元测试**：覆盖 `As`（含 wrap 场景）、`HTTPStatus` 映射、`ErrorOf` 兜底。

## 5. 验收标准

- 所有对外错误均来自 `bizerror` 错误中心，handler 不再出现裸 `response.Error(c, ..., 40100, "...")` 文案。
- 任意层 `fmt.Errorf("xxx: %w", bizErr)` 包装后，经 `ErrorOf` 仍能正确还原业务码。
- 系统错误不泄露内部细节；根因与堆栈仅出现在带 trace_id 的日志中。
- 下游订单服务故障可观测（错误率指标 + 告警），且具备基础重试/熔断保护。
- `docs/error-codes.md` 自动/半自动维护，与代码码表一致。
